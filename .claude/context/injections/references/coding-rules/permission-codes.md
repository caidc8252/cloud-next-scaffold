# Permission codes

A permission code is **4 segments** `<cat>.<mod>.<fn>.<action>`, all lowercase camel, unique within its module and globally (e.g. `system.roles.role.update`). Declare codes in the owning module's `manifest.ts` `permissions[]`. Each code's first two segments (`<cat>.<mod>`) MUST equal the module `menuCode` and each entry's `belongToMenuCode` — `buildRegistry` raises `belongs-to-menu-rule` otherwise.

Granularity: one code per **indivisible capability**. An action that is atomic from the user's view — a multi-step flow that always runs as a unit — shares a single code; do not split it into per-step codes. Split only where the app genuinely guards the parts independently.

MUST be add-only. A code, once shipped, is a contract. To rename or remove one, mark the old code `@deprecated` rather than deleting it (iron law #4) and add the new code alongside. `@deprecated` is author discipline only — `buildRegistry` projects only the current declarations and keeps no deprecated tombstone, so deleting a code from source drops it from the registry outright.

Codes SHOULD be the generated `PermissionCode` values (AGENTS iron law #2 intent). But today `assertPermissions(check: PermissionCheck)` types `check.all` / `check.any` as plain `string[]` (`PermissionCheck = { all?: string[]; any?: string[] }` in `packages/permissions/src/index.ts`), NOT the `PermissionCode` union, and real call sites pass bare string literals (`assertPermissions({ all: ["system.roles.role.update"] })` in `roles.controller.ts`). So a typo / stale / undeclared code is NOT caught by the compiler — it fails at the coc registry / runtime: the referenced code must be declared in a manifest, which `pnpm gen:coc` aggregates into `PermissionCode`. A code an owner hasn't declared yet is referenced via a colocated `*.stub.ts` that exports it `as PermissionCode` (legend → `../cross-module-stub.md`); that cast is what will compile once `assertPermissions` is `PermissionCode`-typed.
