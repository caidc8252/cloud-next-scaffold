# 业务逻辑 — 邀请入驻（invite & onboarding）

> 本文描述邀请/入驻的**核心业务逻辑**（要做成的样子），只写不显然的规则与分支，不写代码机制。
> 字段命名以 `packages/db/prisma/schema.prisma` 为准。两类场景共用同一套邀请底层，但目的与入口完全不同：

- **场景一 · 通用邀请（本期）**：各 Party 平台操作员登录后在 **User 模块**为**自己的 Party** 邀请新操作员。被邀人加入的是一个**已存在且已激活**的 Party，成为普通成员。
- **场景二 · Onboarding 开户（待办）**：ADMIN 平台 **Customer 模块**为**新建的 Party** 创建**第一个管理员**。这是 Party 的开户动作，一次性发生。

> 关键修正：分支判据是**入口/场景**（哪个模块发起），**不是**"是不是 Party 的第一个成员"。场景一恒为普通成员、不激活 Party；首管与激活只属于场景二。
>
> 标 **〔裁决 CONF-N〕** 的规则系**通过冲突裁决获得**（输入 vs 现有代码的冲突，已逐条定案）；裁决全文见 `docs/superpowers/specs/2026-06-14-invite-user-backend-conflicts.md`。

## 场景一 · 通用邀请（本期实现）

### 操作员邀请新成员加入本 Party
操作员在 User 模块填目标邮箱 + 勾选授予角色并提交；邀请落库为 `PENDING`，链接随即发出。
- 授予角色**可多选**，记为邀请的 `intendedRole`；被邀人接受后原样拷入其 Party 成员归属。
- 邀请有效期默认 **7 天**，取自**全局共享配置**（`@cloud/platform-config` 的平台常量，所有子平台共用，不在各 app 硬编码）。〔裁决 CONF-3〕
- 目标邮箱**已是本 Party 成员**（任意状态，含 LOCKED）→ 拒绝重邀（复用 `ERR_USER_EMAIL_TAKEN`）。〔裁决 CONF-2〕
- 目标邮箱在本 Party 有**未过期** PENDING 邀请 → 拒绝（防重复发）。〔裁决 CONF-2 / CONF-4〕
- 目标邮箱在本 Party 仅有**已过期** PENDING 邀请 → **覆盖**该行（重置 token + 有效期 + 角色并重发），不新建第二条、不拒绝。〔裁决 CONF-4〕

### 提供邀请链接（邮件 / 复制 URL）
邀请链接有两种投递方式，本质都是 URL 上的 `token`。
- 链接有效性**只认 URL 上的 token**；邮件发出与网页复制 URL 线下转发是同一 token 的两种等价投递。
- 邮件经 `@cloud/mail` 异步发出；发信失败**不回滚**邀请（已落库，管理员可重发），让背压/频率问题显式可见。

> 邀请上有三个就地操作——**改角色 / 重发 / 重新生成**，**均仅作用于「未过期 PENDING」**；已过期邀请一律不可就地操作，只能用"发送邀请"覆盖（见上）。〔裁决 CONF-4〕

### 修改邀请角色（仅未过期）
操作员可改授予角色——**仅 `PENDING` 且未过期**可改。
- 已过期 → 不可就地改；要改只能用"发送邀请"覆盖。
- 已消费 → 不可改。

### 重发邀请（仅未过期）
原样再寄同一封邀请邮件，**不改 token、不改有效期**。
- 仅未过期 PENDING 可重发；已过期 → 无法重发（链接已死，重寄无意义）。
- 收件人级**节流（60s 冷却）**：连点重发对同一收件人返回限流，提示稍后再试。

### 重新生成邀请（仅未过期）
换发新链接：**重置 token + 刷新有效期（+7d）+ 重发邮件**，用于链接疑似泄露时轮换。
- 仅未过期 PENDING 可重新生成；已过期 → 无法重新生成（改用"发送邀请"覆盖）。
- 旧 token 立即失效（旧链接进失效页）。

### 撤销邀请
操作员可撤销尚未被接受的邀请。
- **仅 PENDING 可撤**；已消费 / 不存在 → 报错（不能撤一封已完成入驻的邀请）。
- 撤销后该 token 立即失效，被邀人再打开链接进失效页。

### 查看成员与待入驻邀请
User 模块的成员列表 = 在册成员 + **待消费邀请**两类同列展示。
- 待消费邀请以 **PENDING 伪条目**出现（非真实用户），让"已发未接受"的邀请可见；未过期可就地重发 / 重新生成 / 改角色 / 撤销，已过期仅能撤销或用"发送邀请"覆盖。

### 被邀请人接受邀请、完成入驻
被邀请人打开链接 → 验票（`PENDING` 且未过期，否则进失效终态页）→ 把这张邀请**绑定**到一个账号（当前登录的 / 既有账号登录的 / 用被邀邮箱新建的）→ 邀请即刻失效 → 建会话进 console。
- **token 是建号 + 绑定 Party 的唯一凭证**，也是唯一安全边界：能打开链接 ≈ 证明收到了发往该邮箱的邮件。
- **一次性**：账号 ↔ Party 绑定（`sys_party_user`）完成即把邀请置为已消费；原子条件更新（仅 `PENDING → CONSUMED`）+ 归属唯一约束，双重防并发重复消费。
- **防滥用**：① 不能无限建号——register 模式邮箱**恒取邀请预置邮箱**，忽略客户端传入的 email；② 不能绑到别的 Party——`partyId` **恒取邀请记录**，客户端不可指定。
- 被邀邮箱**已注册** → 不建第二个账号，引导改用"登录加入"。
- 账号**已是本 Party 成员** → 幂等成功（不重复绑定、不降级角色），提示"你已是成员"并进入。
- 新成员授予角色 = 邀请的 `intendedRole`；授权类型恒为 **NORMAL（普通成员，由邀请操作员授权）**，**不因"是不是 Party 第一个成员"而变**，也不激活 Party。
- **验票失效不泄露主体信息**：token 不存在时进失效页**不透露任何 party 信息**；仅过期 / 已消费才提示对应失效原因。
- **密码明文不出网**（register 与登录同口径）：密码走 **RSA-OAEP + 一次性 nonce + 双向时间戳窗**防重放；服务端解密后**再次校验密码强度**，弱密码即便绕过前端也被拒。
- **入驻后落地去向**按该账号的可选 Party 数派生：
  - 恰好 **1 个可选 Party**（新注册用户必属此类）→ 建会话并**直达对应 console**（按 Party 的 portal 组做跨 host handoff）。
  - **多选 / 零选 / 授权窗口失效**（落不下唯一 Party）→ 进 **`/select-partner` 选择页**，不直达、不签 handoff。

### 既有账号登录后回到邀请页加入
未登录或想换账号时，先去登录，认证后回到邀请页继续 accept。
- 跳 `/login?returnTo=邀请页`；带 `returnTo` 的登录**只建 portal 会话、不跨 host handoff**，认证后跳回邀请页。
- `returnTo` **仅允许站内 `/onboarding` 前缀**，防开放重定向；MFA 场景 `returnTo` 经一次性 `mfaToken` 透传。

## 场景二 · Onboarding 开户（待办，本期不实现）

ADMIN 平台 Customer 模块为新建 Party 创建第一个管理员。目的与场景一不同：这是 Party 的**开户**动作，一次性。
- 仅当 Party **尚无任何成员**（无 `sys_party_user`）时可发 onboarding 邀请；**已有管理员后不能再发**。
- 被邀人接受后授权类型为 **ADMIN**，并**激活 Party**（首个成员加入 → Party 由 `ONBOARDING` 转 `ACTIVE`）。
- 其余规则（多选角色、7天有效期、一次性、token 唯一凭证、防滥用、链接两种投递、重复/失效校验、改角色、重发节流）**与场景一一致**。

## 现状差距（裁决后待实现）

> 上述约定多数已落代码；下列是**现有代码与裁决后约定的差距**，需改代码以符合约定。来源见冲突裁决文档（CONF 编号同上）。

- **首管/激活移出通用 accept**〔CONF-1〕：当前 `accept` 在 party 为 ONBOARDING 时把成员设 ADMIN 并激活 party——属场景二逻辑，需从场景一通用流程剥离；场景一恒 NORMAL、不激活。ADMIN 平台首管来自 seed，无 bootstrap 缺口；Customer 租户首管待场景二。
- **createInvite 补成员校验**〔CONF-2〕：现仅查 pending 邀请，需加"邮箱已是本 Party 成员（任意状态）→ 拒绝"；且"已邀请→拒绝"收紧为仅对**未过期** pending，遇**已过期** pending 走覆盖。
- **配置迁入共享包**〔CONF-3〕：`INVITE_TTL_MS` / `INVITE_TOKEN_BYTES` 从 `apps/admin` 局部常量迁入 `@cloud/platform-config`。
- **生命周期操作按"过期/未过期"重定义**〔CONF-4〕：`setInviteRoles` / `resend` 加未过期守卫；`resend` 去掉有效期刷新（改为只重寄）；**新增**"重新生成"（换 token + 刷有效期 + 重发）；`createInvite` 对已过期 pending 改为覆盖。

## 场景一 / 场景二 复用分析

两场景**目的、入口、权限完全不同**，但底层邀请机制高度一致。

**可直接复用（同一套底层）**：邀请实体 `SysOperatorInvite`、验票、token 一次性原子消费、账号 ↔ Party 绑定 `sys_party_user`、建号（email+password；未来 SSO / 验证码同口径）、发信、链接两种投递、重复/失效校验、改角色、重发节流、会话收尾。

**差异（应作为策略参数，而非分叉成两套流程）**：

| 维度 | 场景一（User 模块） | 场景二（Admin Customer，待办） |
|---|---|---|
| 发起方 / 权限守卫 | Party 操作员，User 模块权限 | ADMIN 平台超管，Customer 模块权限 |
| 目标 Party 状态 | 已存在且 `ACTIVE` | 新建、`ONBOARDING` |
| 被邀人授权类型 | `NORMAL` | `ADMIN`（首管） |
| 是否激活 Party | 否 | 是（首个成员加入即激活） |
| 发起门槛 | 邮箱非本 Party 成员、无在效邀请 | + Party 尚无任何成员（一次性开户） |

**建议方向（不在本期落地）**：把邀请生命周期（create / verify / accept / consume / bind / email / resend / regenerate / edit-roles）沉淀为共享 service，差异项（`authorizingType`、是否激活 party、发起门槛、权限守卫）由各模块以策略参数注入。**本期先保证场景一这套干净无 bug**；待场景二实现时再抽共享层，避免过早抽象。
